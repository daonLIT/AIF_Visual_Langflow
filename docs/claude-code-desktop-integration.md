# Claude Code 구현 지시서: Langflow Desktop → AIF 저장 → 웹 검토

## 1. 요청과 목표

이 저장소의 기존 구현을 확인하고 아래 기능을 실제 구현하라. 계획만 제시하고 끝내지 말고 코드, 마이그레이션, 필요한 테스트, 실행·배포 문서를 완성하라. 기존 작업과 사용자 데이터를 보존하고 저장소의 AGENTS.md가 있으면 먼저 읽어라.

사용자는 Langflow Desktop에서 판결문 분석 Flow를 실행한다. 생성된 AIF 결과는 배포된 우리 백엔드를 통해 DB에 자동 저장된다. Desktop의 사이트 이동 버튼을 누르면 기본 브라우저로 우리 사이트가 열리고, 저장된 원문과 그래프를 파일 업로드 없이 확인·검토·수정할 수 있어야 한다.

사용자 PC에는 Langflow Desktop과 현재 Flow가 사용하는 Ollama 및 모델이 필요하다. 사이트·백엔드·DB는 서버에서 상시 운영한다. 사용자에게 로컬 프런트엔드나 백엔드를 별도로 실행하도록 요구하는 구성을 최종 운영 방식으로 삼지 않는다. 개발·통합 테스트는 로컬에서 가능해야 한다.

## 2. 현재 구현과 재사용 지점

아래는 작성 시 확인한 구조이며 구현 전에 실제 코드를 읽어 세부 동작을 확인하라.

- frontend/: React 19, Vite, React Flow 기반 검토 UI.
- frontend/src/App.tsx: 앱 진입 화면과 논증/파이프라인 화면.
- frontend/src/api/client.ts: 프로젝트 저장·조회 API 클라이언트.
- frontend/src/store/annotationStore.ts: loadFromServer, loadProjectFile, 검토 상태 및 프로젝트 저장.
- frontend/src/components/Toolbar/Toolbar.tsx: 프로젝트 목록·열기·저장 UI.
- backend/: Starlette, Pydantic, SQLite.
- backend/app/routes/api.py: 실행·프로젝트·카탈로그 API.
- backend/app/storage/db.py: analysis_runs, projects 및 명시적 DB 마이그레이션.
- backend/app/schemas/models.py: schemaVersion 2 프로젝트와 요청 모델.
- backend/app/services/aif_adapter.py: 그래프 검증, 실행별 ID 변환, annotation 생성.
- backend/app/services/evidence_matcher.py: 원문 근거 매칭.
- backend/app/services/run_manager.py: 기존 사이트에서 시작하는 분석 관리.
- langflow/components/judgment_splitter.py: 백엔드가 만든 입력 JSON에서 원문·카탈로그 추출.
- langflow/make_v11_flow.py 및 v11 Flow JSON: 기존 Flow 생성 방식.

기존 GET /api/projects, GET /api/projects/{id}, PUT /api/projects/{id}, 카탈로그 API를 가능한 한 재사용하라. 외부 결과를 수신하면서 기존 분석 실행 API를 다시 호출하거나 LLM을 재실행하지 않는다.

현재 Flow는 백엔드가 원문과 함께 쟁점·스킴 카탈로그를 주입하는 구조다. Desktop에서 평문만 입력하면 카탈로그가 비므로, 마지막 저장 노드만 붙이는 작업으로 끝내면 안 된다.

## 3. 목표 아키텍처

```text
사용자 PC
  Langflow Desktop + Ollama
    판결문 입력
      → 실행 컨텍스트 준비 및 서버 카탈로그 조회
      → 기존 분석 Flow
      → Result Validator
      → AIF Publish 컴포넌트
           │ HTTPS 요청
           ▼
운영 서버
  우리 백엔드 → 검증·원문 매칭 → DB 트랜잭션 저장
           │ projectId / runId / viewerUrl 반환
           ▼
Desktop의 [이 결과 보기] → 기본 브라우저
  우리 사이트 → 인증된 프로젝트 조회 → 원문·그래프·검토 화면
```

Desktop과 브라우저가 DB 파일에 직접 접근하지 않도록 한다. 둘 다 동일한 운영 백엔드를 이용한다. Langflow 자체 내부 DB와 우리 프로젝트 DB는 별개다. 사이트가 Desktop의 localhost 서버에 접근해야만 결과를 볼 수 있는 구조로 만들지 않는다.

## 4. Desktop 버튼: 구현 전에 확인할 사항

설치된 Desktop 버전과 포함된 Langflow 버전, UI 소스와 확장 가능 범위를 먼저 확인하라. 저장소 문서의 Langflow 1.11 언급을 실제 설치 버전으로 단정하지 않는다.

공식 참고:
- https://docs.langflow.org/concepts-overview
- https://github.com/langflow-ai/langflow
- https://github.com/langflow-ai/desktop-updates

커스텀 Python 컴포넌트를 만들면 Desktop 상단에 임의의 버튼도 자동으로 추가된다고 가정하지 않는다. Electron 등 Desktop 프레임워크도 확인 없이 전제하지 않는다.

필수 UX:
1. [우리 사이트 열기]: 서버 프로젝트 목록을 기본 브라우저로 연다.
2. 저장 완료 결과의 [이 결과 보기]: 해당 projectId의 검토 화면을 연다.
3. 저장 중·저장 실패·저장 완료를 구분하고, 저장 실패를 성공으로 표시하지 않는다.
4. 이전 실행의 링크를 새 실행 결과로 오인하지 않도록 실행별 결과에 링크를 연결한다.

지원되는 확장 방식이 있으면 사용하고, 없다면 Langflow UI 수정 및 필요한 Desktop 패키징 범위를 명시하여 구현하라. 설치 폴더를 임시로 수정하는 것만으로 완료 처리하지 말고, 재현 가능한 패치·빌드·적용·업데이트 절차를 남겨라. 필요한 외부 소스나 빌드 권한이 없으면 백엔드·Flow·사이트 작업을 먼저 완료하고 버튼 작업의 정확한 차단 요인을 보고하라.

출력 메시지의 클릭 가능한 링크는 초기 통합 검증에 사용할 수 있으나, 실제 버튼 요구사항을 링크로 조용히 대체하거나 버튼 구현 완료로 보고하지 않는다. 외부 URL은 설정된 사이트 출처로 제한하고 사용자 클릭 시 기본 브라우저로 연다. 백엔드 Python의 webbrowser 호출에 의존하지 않는다.

## 5. 실행 컨텍스트와 Flow 수정

기존 Flow 원본을 보존하고 Desktop용 새 버전을 생성하라. 생성 스크립트와 컴포넌트 소스, 생성된 JSON이 일치해야 한다.

### 입력 준비

- 판결문 원문, 사건명/사건 ID, 운영 API 주소, 연동 자격증명을 설정할 수 있게 한다.
- 원문의 공백·줄바꿈을 보존한다.
- 쟁점 및 스킴 카탈로그를 서버에서 읽고 버전·해시와 함께 실행 컨텍스트로 고정한다.
- 새 전체 실행마다 externalRunId를 만들고 마지막 저장 단계까지 동일한 값을 전달한다.
- 저장 단계 재시도는 같은 ID를 쓰고, 실제 새 분석은 새 ID를 쓰도록 Langflow 캐시·노드 재실행 동작까지 검증한다.
- 카탈로그 조회 실패를 빈 카탈로그 분석으로 대체하지 말고 명확한 오류로 종료한다.

### AIF Publish

- 최종 AIF, 원문, 실행 컨텍스트를 입력으로 받는다.
- 반드시 최종 실행 출력 경로에 연결한다. 연결되지 않은 부수 노드 때문에 게시 단계가 생략되면 안 된다.
- 아래 수신 API로 결과를 전송하고 서버 응답의 저장 상태와 viewerUrl을 출력한다.
- 분석 상태와 게시 상태를 구분한다. 그래프 생성 성공 후 업로드 실패 시 생성된 결과를 보존한다.
- 타임아웃·일시적 서버 오류는 제한된 횟수와 지연으로 재시도한다. 인증·검증·내용 충돌 오류는 무한 재시도하지 않는다.
- 앱 재시작 후에도 저장 재시도가 필요하므로 게시 대기 결과를 로컬 outbox에 보존하는 방식을 구현하라. 사용자의 수동 파일 업로드는 요구하지 않는다. 원문·결과를 담는 경로, 접근 제한, 성공 후 정리 정책을 문서화하고 비밀키는 outbox에 저장하지 않는다.
- 서명된 비밀값을 Flow JSON이나 출력 메시지에 포함하지 말고, 설치 버전에서 지원하는 비밀 설정 방식을 사용한다.

## 6. 외부 결과 수신 API

권장 경로: POST /api/integrations/langflow/results

다음은 의미를 정의하는 계약 예시다. 기존 실제 AIF envelope 및 프로젝트 모델에 맞춰 구체적인 Pydantic 모델을 확정하고 문서·테스트와 일치시켜라.

```json
{
  "schemaVersion": 1,
  "externalRunId": "실행별 UUID",
  "source": {"kind": "langflow-desktop", "flowId": "실제 ID", "flowName": "분석 Flow"},
  "document": {"text": "판결문 원문", "caseId": "선택값", "title": "사건명"},
  "catalogs": {"issueCatalogVersion": "버전", "issueCatalogSha256": "해시", "schemeCatalogVersion": "버전", "schemeCatalogSha256": "해시"},
  "result": {"실제 최종 AIF 결과 객체": "기존 어댑터 계약에 맞게 정의"}
}
```

신규 저장은 201, 동일 요청의 재전송은 200으로 반환한다.

```json
{
  "projectId": "서버 생성 ID",
  "runId": "서버 생성 ID",
  "revision": 1,
  "status": "saved",
  "viewerUrl": "https://설정된사이트/?projectId=서버생성ID",
  "duplicate": false
}
```

계약과 처리 규칙:
- 외부 결과 게시 권한을 검증한 뒤 요청을 처리한다.
- 원문 크기, 요청 전체 크기, 그래프 규모 및 필드 타입을 제한한다.
- 서버에서 원문 해시를 계산하고 실제 사용 카탈로그 버전과 결과를 검증한다.
- 실행 도중 서버 카탈로그가 바뀌어도 현재 버전을 사용한 것처럼 기록하지 않는다. 과거 카탈로그 스냅샷을 보관해 검증하거나, 지원하지 않는 버전은 명시적인 오류로 반환한다.
- 실제 실행한 Flow 해시·모델 설정은 수집 가능한 범위에서 비밀값을 제외하고 기록한다. 알 수 없는 정보를 만들어 넣지 않는다.
- 기존 어댑터로 ID namespace 변환, 근거 매칭, 미검토 annotation 생성을 수행한다.
- AI 결과는 acceptedGraph에 자동 확정하지 않는다. 기존 미검토 그래프 표시 기능으로 즉시 보이게 한다.
- 정상 no_issues 결과는 빈 그래프와 사유를 가진 프로젝트로 저장한다. invalid 결과는 정상 프로젝트로 공개하지 않고 명시적 오류로 처리한다.
- 오류 envelope는 기존 API 형식을 따른다. 401/403, 409, 413, 422 등 실패 의미를 구분한다.
- viewerUrl은 신뢰된 서버 설정에서 생성하며 요청이 제공한 임의 URL을 그대로 반환하지 않는다.

## 7. 저장 일관성 및 마이그레이션

- 기존 analysis_runs와 projects를 재사용하고 필요한 외부 게시 메타데이터 또는 매핑 테이블만 추가한다.
- 인증 주체/연동 ID와 externalRunId 조합에 DB UNIQUE 제약을 둔다. 요청의 source 값으로 인증 주체를 결정하지 않는다.
- 정규화한 요청 내용의 해시를 보관한다. 같은 실행 ID·같은 내용은 기존 ID를 반환하고, 같은 실행 ID·다른 내용은 409로 처리한다.
- 실행 기록·프로젝트·게시 매핑을 하나의 트랜잭션으로 커밋한다. 기존 개별 저장 함수의 내부 commit으로 부분 저장이 생기지 않게 한다.
- 병렬 중복 요청, 커밋 후 응답 유실과 재전송에도 프로젝트가 하나만 생성되어야 한다.
- 재전송 시 사용자가 이미 수정한 프로젝트를 최초 AI 결과로 덮어쓰지 않는다.
- 새 분석은 별도 프로젝트/실행으로 보존한다. 동일 사건의 결과는 사건 ID로 구분·조회할 수 있게 한다.
- 기존 revision 충돌 검사를 유지한다.
- 기존 명시적 마이그레이션과 백업 체계를 따른다. DB 초기화로 해결하지 않는다.

초기 단일 서버 운영은 SQLite와 영구 볼륨으로 가능하다. 여러 프로세스/서버가 DB를 공유하는 운영이 필요하면 PostgreSQL 전환 범위를 별도로 설명하라. 브라우저·Desktop에 SQLite 파일을 복제하는 방식은 사용하지 않는다.

## 8. 사이트 변경

- ?projectId=... 진입 시 기존 loadFromServer를 이용해 원문·실행 기록·미검토 그래프·검토 이력을 불러온다.
- 파라미터 없이 접속하면 서버 프로젝트 목록을 기본 진입 화면으로 제공한다.
- 목록에는 사건명, 저장 시각, 실행 출처, 구분 가능한 프로젝트 정보를 표시한다.
- 로딩·인증 필요·없음·권한 없음·서버 오류를 구분한다.
- 로그인 후 원래 projectId 목적지로 복귀하게 한다.
- 새로고침 및 직접 URL 접근을 지원하고 중복 초기화·늦게 도착한 요청의 상태 덮어쓰기를 방지한다.
- 편집 중 다른 프로젝트로 이동할 때 미저장 변경 보호를 유지한다.
- 서버 저장과 재접속 후 검토·수정 결과가 유지되어야 한다.
- 기존 한국어/영어 메시지 체계를 따른다.
- 기존 사이트 분석·파이프라인 편집 기능을 삭제하지 않는다. 새 기본 동선은 프로젝트 목록과 검토로 두고 기존 기능은 보조 진입점으로 유지한다.
- Desktop에서 가져온 결과를 열기 위해 Langflow 서버 연결이나 새 Flow 실행을 요구하지 않는다.

## 9. 운영 배포와 인증

현재 문서는 로그인·외부 배포를 기존 범위 밖으로 설명한다. 이번 목표는 원격 서버 운영이므로 공개 배포 전에 접근 제어를 구현해야 한다.

- 단일 소유자/팀 환경을 초기 범위로 삼고, 복잡한 회원가입 서비스를 불필요하게 추가하지 않는다.
- Desktop 게시용 자격증명과 브라우저 로그인 세션을 구분한다. 연동 토큰에는 필요한 카탈로그 읽기·게시 권한만 부여한다.
- 기존 프로젝트 목록·조회·수정 API에도 접근 제어를 적용한다. UUID를 안다는 사실을 권한으로 취급하지 않는다.
- 기존 파이프라인 수정·코드 관련 API가 익명으로 노출되지 않도록 전체 API 접근 경계를 점검한다.
- 쿠키 인증이면 Secure/HttpOnly/SameSite와 변경 요청 CSRF 방어를 적용한다.
- 토큰을 URL, 프런트엔드 번들, Flow 내보내기, 로그에 노출하지 않는다. 원문·그래프 전체도 기본 로그에 남기지 않는다.
- 가능하면 프런트엔드와 /api를 같은 HTTPS 출처로 제공한다. Desktop의 서버 간 HTTP 요청을 CORS로 인증하려 하지 않는다.
- API 주소, 공개 사이트 주소, 영구 DB 경로, 인증 관련 환경변수와 예시를 문서화한다.
- 서버 DB 백업·복구, 재시작, 상태 확인 및 인증키 교체 절차를 제공한다.
- 서버가 Langflow/Ollama 없이도 외부 결과 저장·조회·검토를 제공할 수 있도록 시작 조건과 health 상태를 분리한다.

호스팅 주소·계정이 제공되지 않았다면 이를 발명하거나 실제 공개 배포 완료라고 보고하지 않는다. 로컬 검증과 배포 가능한 구성·문서를 완성한 뒤 필요한 운영 설정을 구체적으로 보고하라.

## 10. 구현 순서

1. 기존 코드와 Desktop 버전·버튼 구현 가능 경로 확인. 최종 아키텍처와 차단 요인 기록.
2. 결과 수신 모델, 공통 결과 처리 서비스, 마이그레이션, 원자적 게시 저장 및 인증 구현.
3. 프로젝트 URL 자동 로드, 프로젝트 목록 진입 화면 구현.
4. Desktop 입력 준비·카탈로그 주입·결과 게시·재시도/outbox 및 새 Flow 생성.
5. Desktop의 사이트 열기·결과 보기 버튼과 재현 가능한 UI 적용 방식 구현.
6. 운영 설정·접근 제어·영구 저장·배포 문서 작성.
7. 통합·회귀 검증 및 실제 확인 범위를 기록.

## 11. 검증 및 완료 기준

의미 있는 서버·컴포넌트·프런트엔드 테스트를 추가하고 기존 필수 검사를 실행하라.

기존 검사 진입점:
- backend: python run_tests.py
- frontend: npm run check
- Flow 생성 검증: 기존 생성 스크립트 방식에 맞춰 Desktop Flow 재생성 및 결과 확인

필수 시나리오:
- Desktop 실제 Flow 실행 → DB 저장 → 버튼 클릭 → 같은 원문·AIF 표시. 수동 업로드 0회.
- 사이트를 먼저 열면 기존 저장 목록을 볼 수 있음.
- Desktop을 종료해도 저장 결과 조회와 편집 가능.
- 사이트에서 수정·저장 → 새로고침/재접속 후 동일 상태 유지.
- 정상 no_issues 결과와 invalid 결과 구분.
- 잘못된 그래프 참조, 빈 원문, 과도한 요청 크기, 카탈로그 불일치 처리.
- 같은 게시 요청 반복·동시 전송·응답 유실 재시도에도 중복 프로젝트 없음.
- 같은 실행 ID의 다른 내용은 409, 새 전체 실행은 별도 결과.
- DB 실패 시 부분 저장 없음, 기존 데이터 마이그레이션 후 유지.
- 네트워크 단절 후 저장 단계만 재시도, Desktop 재시작 후 outbox 복구.
- 인증 없는 목록/조회/저장/게시 차단, 연동 토큰의 불필요한 권한 차단.
- deep link 로그인 복귀, 존재하지 않는 ID, 미저장 편집 보호.
- 기존 사이트 분석·프로젝트 불러오기·검토·revision 충돌 처리 회귀 없음.

실제 Desktop·Ollama를 실행할 수 없으면 fixture 또는 mock 검증과 실제 E2E 미확인 부분을 구분한다. 링크만 만들고 버튼까지 검증했다고 보고하지 않는다.

## 12. 최종 산출물 및 보고

- 백엔드·프런트엔드 변경 코드와 DB 마이그레이션.
- Desktop용 Flow JSON, 컴포넌트 소스 및 재생성 도구.
- 실제 버튼 구현 또는 재현 가능한 UI 패치·빌드 산출물. 불가하면 정확한 차단 사항.
- 환경변수 예시, 사용자 설치·설정 안내, 서버 운영·배포·백업 문서.
- API 계약과 재시도·중복 방지 정책 문서.
- 테스트 결과 및 실제 E2E 증거. 키나 판결문 원문은 증거에 노출하지 않는다.

최종 보고에는 구현한 동작, 사용 방법, 실행한 검사와 결과, 미검증 항목, 운영에 필요한 설정을 적어라. 모든 필수 흐름을 검증하기 전에는 전체 완료라고 표현하지 않는다.
